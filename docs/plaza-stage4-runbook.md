# 광장 4단계 로컬 시험·파기 실행 절차

기준: 2026-10-04, `feat/plaza-stage4-20261004`. 기존 0단계 설계와 `plaza-stage4-privacy-and-school.md`를 함께 읽는다.

## 준비

Node 22 이상, 기존 앱 의존성과 별도 `plaza_test_*` PostgreSQL을 사용한다. `PLAZA_STAGE1_TEST=1`, `PLAZA_STAGE2_TEST=1`, `PLAZA_STAGE3_TEST=1`, `PLAZA_STAGE4_TEST=1`, 새 UUID인 `PLAZA_TEST_ID`, 저장소 밖의 절대 경로인 `PLAZA_TEST_STORAGE_DIR`를 지정한다. DB 주소는 loopback만 허용하며 `VERCEL` 환경에서는 시작을 거절한다. 운영 DB·기존 버킷으로 대체하지 않는다.

`PLAZA_SETUP_CONFIRM=disposable-local-test`에서 `node scripts/plaza-stage4-setup.js`를 실행하면 기존 1~3단계 시험 준비 후 `db/plaza-stage4.sql`을 별도 적용하고 가짜 관리자 자격 증명을 비공개 `fixture.json`에 저장한다. 관리자 비밀번호를 터미널·문서·저장소에 복사하지 않는다. 실제 키트·AI 제공사는 이 설정으로 승인되지 않는다. 가짜 카드 시험에는 기존 `PLAZA_SYNTHETIC_KIT=1`을 사용한다. 교안 파일은 기존 별도 비공개 경로로 등록한다.

새 SQL은 `lib/db.js`의 자동 마이그레이션에 포함하지 않는다. 수동 설치가 성공한 뒤 앱을 실행한다. 관리자 계정으로 `/class#/plaza-retention`에서 수업별 시험 보관 시간을 먼저 등록한다. 기본값은 없고 입장 전 한 번만 확정한다. 학생 입장 화면에도 이 기간과 시험 안내를 보여 준다.

## 실행 순서

1. 관리자가 사진·활동·운영 이력의 시험 시간을 입력한다. 운영 이력은 사진·활동보다 일찍 파기되도록 등록할 수 없다.
2. 가짜 학생은 수업 코드 로그인 후 기록·사진을 각각 선택한다. 기록 없이 참여하는 학생에게는 진로기록 학생 UUID를 만들지 않는다.
3. 기존 구상→제작→개장→교류→돌아보기 흐름을 진행한다. 기록 선택 학생은 최종 원본 저장, 비기록 학생은 ‘활동 완료’로 마친다.
4. 학생의 사진 중지 요청은 새 촬영·조회부터 막고 삭제를 실행한다. 실패 상태에서는 같은 버튼을 다시 눌러 확인할 수 있다.
5. 수업 종료 또는 코드 이용 만료 후 관리자가 보관·파기 화면에서 기한·목록을 다시 확인한다. 종료·자료 잠금·학생 이용 만료가 관리자의 파기 기능을 막지 않는다.
6. 파기할 범위를 확인하고 실행한다. 서버는 미리보기의 버전·범위·파일 목록 해시를 재확인한다. 목록이 바뀌었다면 다시 확인한다.
7. `retry`인 작업은 같은 작업의 파일 부재 재확인·재시도를 실행한다. `verified`는 해당 광장 범위의 검증이며 전체 시스템 파기 완료가 아니다.
8. 등록되지 않은 파일은 별도 고아 파일 목록으로 확인하고 실행한다. 전용 폴더의 정확한 UUID `.jpg`와 해당 UUID의 `.tmp` 파일만 대상이며, 등록된 타 수업 파일이나 다른 이름의 파일을 함께 삭제하지 않는다.

이 시험 버전의 보관 기한은 **수동 실행할 파기 대상의 계산**이다. 자동 작업 스케줄러·운영 버킷 파기 어댑터·실패 알림 서비스가 설치됐다는 뜻이 아니다. 실제 운영 전에는 실행 주기·책임자·실패 알림과 대응 시간을 확정하고 별도 검증해야 한다.

## 서버 처리와 완료 기준

| 범위 | 완료 전에 확인하는 것 |
|---|---|
| 사진 철회 | 사진 선택 중지, 전시 연결 해제·대상 버전 변경, 저장된 이전본과 임시본까지 파일 목록 포함 |
| 보관 기한 파기 | 수업 종료·접속 폐기, DB 외부의 삭제 목록 기록, 조회 차단 |
| 파일 삭제 | 삭제 요청의 결과와 실제 디렉터리 부재를 모두 확인. 실패하면 DB 사진 행을 남기고 재시도 상태 유지 |
| 활동 파기 | 광장 초안·AI 실행 내역·교류·활동·최종 접수 사본·쓰기 응답 원문 삭제 |
| 운영 이력 파기 | 사진·활동 파기 완료 후 재발급·기기 권한·이벤트·운영 작업·참여자 연결 삭제 |
| 파기 이력 | 최소 작업 번호·무작위 파일 번호·시각·처리 범위·실패 코드 보존. `whole_system_complete`는 항상 false |

4단계 사진 전송은 수업 행 잠금을 유지한 채 파일 쓰기와 검증을 마친다. 파기가 먼저 끝났는데 이전 업로드가 뒤늦게 파일을 다시 만드는 상황을 막는다. 원장 파일은 임시 파일에 기록·동기화한 뒤 원자적으로 교체한다. 앱 자체의 비공개 파일 저장소 구현만 검증한 것으로, 네트워크 오브젝트 저장소의 일관성·백업까지 검증한 것은 아니다.

사진의 기존 등록 파일·재촬영본·예약된 임시 파일은 수업 파기 대상이다. 소유 수업을 알 수 없는 고아 파일은 특정 수업에 임의 배정하지 않고 별도 관리자 목록에서 삭제한다. 현재 썸네일은 만들지 않는다. 파생본을 추가하면 등록·권한·보관·파기 확인을 함께 추가해야 한다.

## 복원 때 반드시 할 일

최신 `.plaza-purge-ledger`는 DB 스냅샷과 별개의 삭제 증빙이다. 예전 DB나 사진 폴더의 사본으로 이 최신 원장을 덮어쓰면 안 된다. 운영 도입 시 최신 원장의 별도 보호·복제·접근 권한·최종 보존 종료 정책도 확정해야 한다. 이 로컬 폴더가 운영 재해복구 서비스를 대신하지 않는다.

1. 일반 사용자 접근을 닫은 상태에서 최신 원장과 파기 이력을 먼저 보존한다.
2. DB 또는 파일을 복원하더라도 최신 원장을 유지한다. 원장을 잃었거나 최신 여부를 증명하지 못하면 학생 접속을 열지 않는다.
3. 관리자가 수업을 선택하고 ‘복원 후 삭제 목록 재적용 확인’→범위 확인→‘파기 실행’을 누른다. 아직 기한이 다시 오지 않았더라도 기존 삭제 범위가 적용된다.
4. 이전 DB에 되살아난 초안·교류·접수 사본·참여자와 복원된 파일을 다시 삭제하고 파일 부재를 확인한다. 사진 중지 표식도 유지한다.
5. 고아 파일 목록을 다시 확인한다. 재생성된 파일은 파기 원장과 대조해 다시 처리한다.
6. 진로기록 원본, 백업 매체, 내보내기·종이 사본의 책임자는 각자의 증빙을 확인한다. 이번 기능으로 그 범위까지 끝났다고 보고하지 않는다.

이전 `verified` 작업도 파일 부재를 다시 검사한다. 복원으로 그 작업에 없던 파일이 추가됐으면 작업 재시도를 거절하고 새 미리보기로 범위를 확인하도록 한다. DB만 이전 시점으로 되돌려도 수업 삭제 표식이 일반 조회를 차단하며, 사진 파일 표식은 원본이 다시 생겨도 읽기·쓰기를 거절한다.

## 검증 실행

`npm run check`, `npm test`로 구문과 기존 단위 검증을 실행한다. HTTP 통합 검증은 별도 비어 있는 시험 DB·폴더에 설치한 뒤 `scripts/plaza-stage4-verify.js`의 `installFaults()`를 **서버 모듈을 읽기 전에 시험 프로세스에서만** 설치하고, 서버 시작 후 `verify({fixture,faults})`를 호출한다. 예외 주입용 HTTP 경로나 운영 플래그는 없다.

검증 함수는 가짜 계정·사진·장기 기록을 생성하고 사진·활동·이력을 실제로 삭제하며, 테스트 목적의 이전 행·파일 복원을 수행한다. 일회용 DB·폴더 외에는 실행하지 않는다. 같은 수업으로 다시 실행하지 말고 새 시험 환경을 준비한다. 자격 증명과 DB 사본은 비공개 시험 폴더 밖으로 내보내지 않는다.

이번 실행은 PGlite의 PostgreSQL 엔진과 실제 Node HTTP 경로·파일시스템을 사용했다. 실제 PostgreSQL 다중 연결 경합, iPad/Safari/Chrome 카메라·화면, 운영 Storage·백업 삭제는 별도 현장 검증 대상이다. 시험 결과 수치는 `plaza-stage4-report.md`에 기록한다.
